## Overview

OryqDB is an open-source (`MIT OR Apache-2.0`), embedded, serverless, single-file NoSQL document database engine written in Rust. It provides a native Rust API (`oryq-core`), a diagnostic and maintenance CLI (`oryq` in `oryq-cli`), and a panic-safe C application binary interface (`oryq_*` in `oryq-ffi` and `include/oryq.h`). Target users are systems, desktop, mobile, edge, and language-binding developers who need MongoDB-style document storage, nested-field indexing, and multi-stage query pipelines inside a single portable file across Linux, Windows, and macOS (x86-64 and ARM64) without running an external database server or managed runtime.

To compete directly with SQLite (including SQLite + JSONB) and LiteDB, OryqDB centers on three architectural mechanisms:
1. **OryqDoc Binary Format & State-Normalized Slotted-Page Deltas:** A little-endian binary document format with a sorted field-offset directory header for $O(\log k)$ zero-copy field extraction, combined with bounded page-local normalized value patches (`$set`, `$inc`, `$unset`, `$push`, `$pull`) guarded by a 64-bit field-hash bloom bitmask in the slot header.
2. **Logical-Page WAL B+ Tree with Dual-Mode MVCC Coordination:** A page-oriented slotted B+ tree with stable logical page IDs and an append-only Write-Ahead Log (`.oryq-wal`) indexed by an in-memory Page-Version Indirection Map. In default Single-Process Multi-Threaded mode, the engine acquires one exclusive OS file lock at `Database::open()` (tracked in an in-process inode registry) and runs lock-free MVCC snapshot reads alongside a zero-delay leader-follower group-commit writer with zero per-transaction OS lock syscalls. An opt-in Shared Multi-Process mode coordinates across OS processes via raw-pointer atomics and kernel byte-range heartbeat locks in a `.oryq-shm` sidecar.
3. **MongoDB-Style Query, Indexing & Modular Search Substrate:** Primary, prefix-compressed compound (with restart intervals), and multi-key array B+ tree indexes using order-preserving memcomparable keys, a memory-bounded streaming cursor and aggregation pipeline engine (`$match`, `$project`, `$group`, `$sort`, `$limit`, `$skip`, `$unwind`, `$lookup`), and a WAL-backed `PluggableIndex` substrate that supports compile-time feature-gated Full-Text Search (`oryq-fts`) and Vector Search (`oryq-vec`) crates without expanding the base binary footprint.

## Analysis

### 1. Eliminating the Storage Engine Contradiction: Logical-Page WAL B+ Tree vs. Physical Copy-on-Write (`egm-design`, `egm-codebase-details`, `egm-zoom-out`, `egm-inventive-catalyst`)

* **Contradiction Identified:** All seven Goldfish lenses flagged a conflict in describing the storage engine as a "Copy-on-Write / WAL hybrid B+ tree with page-local deltas." In a physical Copy-on-Write (CoW) B+ tree (such as LMDB or `redb`), modifying any byte on a leaf page allocates a new page ID and rewrites every ancestor internal page up to the root ($O(\text{height})$ full-page writes per commit). That cascading rewrite negates the write-amplification savings of small page-local deltas, introduces dual free-space reclamation protocols (CoW epoch freelists plus WAL checkpointing), and violates Section 5.1 of `docs/draft-spec.md`.
* **Inventive Resolution (TRIZ Pattern 8 — Intermediary & Pattern 2 — Extraction):**
  * Drop physical on-disk shadow-paging CoW. Use **stable logical page IDs** in a **Page-Oriented Slotted B+ Tree with Write-Ahead Logging (`.oryq-wal`) and a Lock-Free MVCC Page-Version Indirection Map**.
  * Updating a document on a leaf page never rewrites parent B+ tree nodes unless the leaf splits. Instead, the writer appends a dirty page frame (or physiological slot-delta frame followed by a full-page image after checkpoint to prevent torn pages) to `.oryq-wal` and publishes `(LogicalPageId, CommitTxId) -> FrameLocation (BufferPoolFrame | WalFrameOffset)` in the Page-Version Indirection Map.
  * Readers load the current committed `SnapshotTxId` via a single atomic read and resolve the latest page version $\le \text{SnapshotTxId}$ without blocking the writer.
* **Bounded Snapshot Leases (TRIZ Pattern 4 — Beforehand Cushioning & Pattern 7 — Blessing in Disguise):**
  * A leaked or stalled reader cursor in an embedded library can pin an old `SnapshotTxId`, preventing WAL checkpointing and causing unbounded RAM or `.oryq-wal` disk growth.
  * To prevent OOM and disk exhaustion, old MVCC page versions evict from the bounded buffer pool (`max_cache_bytes`) back to on-disk `.oryq-wal` frames, and snapshots are governed by `max_wal_size_bytes` and `max_snapshot_duration`. If a stalled reader pins WAL reclamation past the configured ceiling, its next cursor step returns `ORYQ_ERR_SNAPSHOT_TOO_OLD` rather than starving disk space.
* **Ideal Final Result:** Writers append only modified leaf frames sequentially to `.oryq-wal` without cascading parent rewrites, while readers execute wait-free MVCC snapshot reads within a strictly bounded memory and disk footprint.

### 2. Preserving $O(\log k)$ Zero-Copy Reads Under Slotted-Page Deltas (`egm-design`, `egm-codebase-details`, `egm-comprehension`, `egm-structural`, `egm-inventive-catalyst`)

* **Contradiction Identified:** `OryqDoc` provides $O(\log k)$ zero-copy field extraction via a fixed-stride sorted field-offset directory header (`[magic_version: u8, flags: u8, field_count: u16, payload_len: u32]` followed by 12-byte directory entries `[name_hash_prefix: u32, name_offset: u32, val_offset: u32]`). However, if partial updates (`$set`, `$inc`, `$unset`, `$push`, `$pull`) chain operation logs onto the slotted page, readers can no longer binary-search the base header directly: they must scan $D$ deltas ($O(D + \log k)$) and heap-allocate materialized values for relative mutations (`$inc`, `$push`, `$pull`). Furthermore, if `storage/` must evaluate MongoDB operator semantics during page-split compaction, low-level page management becomes coupled to query language semantics.
* **Inventive Resolution (TRIZ Pattern 3 — Preliminary Action, Pattern 1 — Segmentation, Pattern 6 — Dynamics):**
  1. **State-Normalized Value Patches at Write Time:** The `document/` layer evaluates `$inc`, `$push`, and `$pull` during the write transaction (which is already required to compute old and new keys for secondary index maintenance) and emits a **physical field-replacement value patch** (or `$unset` tombstone) keyed by field path hash and offset. The `storage/` layer treats base records and normalized patches through a pure `RecordCompactor` trait without knowing MongoDB update operator rules.
  2. **64-Bit Field-Hash Bloom Bitmask in Slot Directory:** Every slotted-page directory entry carries a 64-bit path-hash bloom bitmask and `delta_count: u8` (`MAX_DELTA_CHAIN = 4`, and total delta bytes $\le 25\%$ of base document bytes). If `delta_count == 0` or the queried field's two hash bits are `0` in the slot's 64-bit bitmask, the reader skips delta inspection in $O(1)$ register time and performs a direct $O(\log k)$ binary search on the base `OryqDoc` directory. If the bits match, the reader takes the newest pre-computed normalized value slice from the bounded delta chain in $O(1)$ zero-copy time.
  3. **Eager Slot Compaction & Overflow Boundary:** When a document's delta count exceeds 4, or when a delta overflows inline slotted-page capacity (`PAGE_INLINE_THRESHOLD = page_size / 4`, 2048 bytes on an 8192-byte page), the writer compacts that slot into a flat `OryqDoc` in memory before deciding whether to allocate overflow pages or split the B+ tree leaf.
  4. **Unaligned-Safe Scalar Decoding:** Because variable-length UTF-8 strings interleave with numbers in `OryqDoc`, zero-copy getters return borrowed byte/UTF-8 slices (`&'a str`, `&'a [u8]`, `OryqDocView<'a>`) and decode fixed-width scalars via unaligned-safe little-endian byte reads (`i64::from_le_bytes`, `f64::from_le_bytes`), never via raw pointer casting (`&i64`), avoiding unaligned memory access undefined behavior.
* **Secondary Operational Trade-offs:** Adds 8 bytes per slotted-page directory entry for the bloom bitmask and requires reading the current field value on write before emitting an `$inc`/`$push`/`$pull` patch.
* **Ideal Final Result:** Unmodified fields resolve in $O(\log k)$ zero-copy time via a single bitmask instruction, modified fields resolve to a contiguous normalized value slice without read-time allocation, and `storage/` remains decoupled from MongoDB operator rules.

### 3. Safe Zero-Copy Lifetimes Across Rust and C ABI (`egm-design`, `egm-codebase-details`, `egm-comprehension`, `egm-inventive-catalyst`)

* **Contradiction Identified:** Returning zero-copy references directly from a bounded buffer-pool page cache requires pinning cache frames. If callers hold document views across long scans, they pin every page and deadlock the cache. Across the `oryq_*` C ABI, returning raw pointers into cache frames causes Use-After-Free (UAF) memory corruption if the C caller steps the cursor or closes the transaction, while forcing JSON serialization across FFI erases `OryqDoc`'s speed advantage over SQLite.
* **Inventive Resolution (TRIZ Pattern 5 — Inversion & Pattern 10 — Cheap Dispensables):**
  * **Rust Two-Tier Document API:**
    1. `OryqDocView<'cursor>`: An ephemeral lending view tied to the cursor's currently pinned leaf `PageGuard`. Advancing `cursor.next_view()?` automatically unpins the previous leaf page before pinning the next, guaranteeing at most one pinned leaf page per cursor.
    2. `OryqDocBuf`: An owned, reference-counted immutable buffer (`Arc<[u8]>`) supporting the same $O(\log k)$ field directory lookup without deserializing into a heap `HashMap`, plus `serde` integration (`Collection<T: Serialize + DeserializeOwned>`).
  * **C ABI (`include/oryq.h`) Dual Path & Panic Containment:**
    1. Ephemeral cursor getters (`oryq_cursor_get_utf8(cursor, path, path_len, &out_ptr, &out_len)`, `oryq_cursor_get_i64(...)`) return `(ptr, len)` slices valid strictly until the next `oryq_cursor_next()` or `oryq_cursor_close()` call (matching `sqlite3_column_blob` lifetime rules).
    2. Standalone `oryq_doc_t *` handles created via `oryq_cursor_clone_doc()` or `oryq_doc_from_json()` wrap an owned `OryqDocBuf` valid until `oryq_doc_free()`.
    3. Every `extern "C" fn oryq_*` wraps its body in `std::panic::catch_unwind`, converting panics to `ORYQ_ERR_INTERNAL_PANIC`, and records diagnostics queryable via `oryq_last_error_message()`. Handle thread-safety is explicit: `oryq_db_t` is `Send + Sync`; `oryq_txn_t`, `oryq_cursor_t`, and `oryq_doc_t` are `Send + !Sync`.

### 4. Dual-Mode Concurrency, CLI Safety & Crash-Proof `.oryq-shm` (`egm-design`, `egm-codebase-details`, `egm-zoom-out`, `egm-comprehension`, `egm-implementation-readiness`, `egm-inventive-catalyst`)

* **Contradiction Identified:**
  1. If Single-Process mode takes no OS file locks, running the `oryq` CLI or a second process against an active database corrupts the file. Furthermore, on POSIX systems, closing *any* file descriptor for an inode drops all `fcntl` locks held by that process.
  2. In Shared Multi-Process mode (`.oryq-shm`), creating Rust `&[u8]` or `&ShmHeader` references over memory-mapped shared memory mutated by another process is immediate Undefined Behavior (LLVM `noalias` data race). Moreover, user-space spinlocks/mutexes inside `.oryq-shm` deadlock permanently if a holding process dies via `SIGKILL`.
* **Inventive Resolution (TRIZ Pattern 3 — Preliminary Action & Pattern 9 — Self-Service):**
  1. **Unified `SnapshotCoordinator` Trait & Connection-Lifetime OS Lock:** Both concurrency modes implement a single `SnapshotCoordinator` trait. At `Database::open()`, the engine checks a process-global `(dev, inode)` registry (preventing the POSIX `close()` lock-drop trap) and acquires an OS byte-range lock on the file header: an exclusive lock in Single-Process mode (zero per-transaction syscalls thereafter, and immediate `ORYQ_ERR_LOCKED_BY_PROCESS` with a diagnostic hint if a second process or CLI tries to write), or a shared mode lock when Multi-Process mode is enabled.
  2. **Zero-Delay Leader-Follower Group Commit:** To avoid adding timer latency to single-threaded writes, the first arriving writer thread becomes the leader and flushes its WAL batch immediately with zero sleep delay, while concurrent writer threads arriving *during* an active `fdatasync`/`FlushFileBuffers` accumulate into the follower ring for the next immediate flush.
  3. **Raw-Pointer Atomics & Kernel Heartbeat Slots in `.oryq-shm`:** `.oryq-shm` is strictly an ephemeral WAL-frame and reader-watermark index (all durable data lives in `.oryq` and `.oryq-wal`). All reads/writes to `.oryq-shm` use raw pointer atomic intrinsics (`*const AtomicU64` with `Acquire`/`Release` ordering, zero Rust slice references). Each connected process holds a 1-byte OS kernel file lock on its assigned reader/writer slot offset in `.oryq-shm`; if a process is terminated via `SIGKILL`, the OS kernel releases its 1-byte lock immediately, allowing any peer process to probe the lock and reclaim the dead slot without deadlocking.

### 5. Indexing, Memory-Bounded Pipelines & WAL-Backed `PluggableIndex` (`egm-design`, `egm-codebase-details`, `egm-zoom-out`, `egm-comprehension`, `egm-implementation-readiness`, `egm-structural`, `egm-inventive-catalyst`)

* **Order-Preserving Memcomparable Key Encoding & Prefix Restart Intervals:**
  * Secondary and compound B+ tree keys encode values into a byte-lexicographically sortable (`memcmp`) format: a 1-byte canonical type rank (`MinKey < Missing/Null < Bool < Number < UTF-8 String < ObjectId/UUID < Binary < Array < Object < MaxKey`), sign-flipped big-endian integers, IEEE-754 sign/exponent-normalized floats (with unified `i64`/`f64` numeric comparison and canonical `-0.0`/`NaN`), and null-escaped strings (`\x00\x01`, terminated by `\x00\x00`).
  * To prevent prefix compression from degrading leaf-page lookups from $O(\log N)$ binary search to $O(N)$ linear scans, prefix-compressed index pages store a full uncompressed key every $R = 16$ slots (**Restart Points**).
  * To prevent Cartesian index explosion ($|A_1| \times |A_2|$ entries per document), compound multi-key indexes enforce MongoDB's rule: at most one indexed field per compound index may hold an array within any single document.
* **Memory-Bounded Aggregation & Streaming Cursors:**
  * Non-blocking stages (`$match`, `$project`, `$limit`, `$skip`, `$unwind`) stream in $O(1)$ cursor memory.
  * Blocking stages (`$group`, unindexed `$sort`), multi-key `DocId` deduplication bitmaps, and snapshot-consistent `$lookup` joins are governed by a per-query memory ceiling (`max_query_memory_bytes`, default 32 MiB), utilizing top-$K$ min-heaps for `$sort + $limit` and spilling intermediate partitions to temporary disk pages (or returning `ORYQ_ERR_QUERY_MEMORY_LIMIT`) when exceeded.
* **WAL-Backed `PluggableIndex` Substrate & Feature-Flag Safety (`oryq-fts`, `oryq-vec`):**
  * To satisfy Section 7.5 and Section 25 of `docs/draft-spec.md`, `oryq-fts` and `oryq-vec` are isolated in separate workspace crates (`crates/oryq-fts`, `crates/oryq-vec`) behind compile-time Cargo feature flags (`fts`, `vec`) and deferred to Phase 3 after the core B+ tree engine is verified.
  * The core `PluggableIndex` trait forbids raw filesystem sidecars: plugins receive a transactional `IndexStorageContext<'tx>` that allocates pages from the main `.oryq` file and logs mutations through `.oryq-wal`, using a two-tier pending-delta B+ tree batch hook (`on_commit_batch`) and candidate `DocId` bitmap pushdown (`search_with_filter`) so FTS/HNSW updates do not stall single-document commits.
  * The file header records `required_write_features` bitmasks: if a build compiled without `fts` or `vec` opens a database containing an active FTS/Vector index, read queries on B+ tree indexes succeed, while writes to the affected collection fail deterministically with `ORYQ_ERR_UNSUPPORTED_FEATURE` instead of silently desynchronizing the index.

### 6. Observability, Deterministic Fault Injection & Documentation Taxonomy (`egm-codebase-details`, `egm-implementation-readiness`, `egm-structural`)

* **Deterministic Virtual File System (`StorageIo`) for Crash Testing:**
  * Group commit and checkpoint compaction run over an injectable `StorageIo` trait supporting deterministic failpoints on `read_at`, `write_at`, `sync_data`, and `truncate`, enabling the subprocess crash-recovery harness (`docs/draft-spec.md` Section 18.5) to test all 7 failure points reproducibly without wall-clock sleeps.
* **Runtime Telemetry & Forensic CLI Tooling:**
  * Expose zero-allocation atomic metrics (`db.stats()`, `oryq_db_stats()`, `oryq info --stats`, `oryq inspect-locks`) covering active readers, oldest pinned `SnapshotTxId`, WAL frame count/bytes, delta chain traversals, in-page compactions, and cache hit rates.
  * Corruption errors return structured forensic context (`{source, page_or_frame_id, file_byte_offset, expected_checksum, actual_checksum, reason}`), supported by `oryq integrity-check --verbose`, `oryq page-inspect`, `oryq wal-inspect`, and `explain_analyze()`.
* **Canonical `docs/` Taxonomy:**
  * Reconcile Sections 3, 22, 27, and 30 of `docs/draft-spec.md` into three non-overlapping documentation groups in `docs/`:
    1. `docs/research/` (9 Milestone 0 research reports: LiteDB architecture, feature inventory, storage, query, concurrency, performance, competitor comparison, initial architecture decisions, and implementation roadmap).
    2. `docs/` Subsystem Specifications (8 documents each following the 10-section template of Section 27: `architecture.md`, `file-format.md` covering `.oryq` / `OryqDoc` / `.oryq-wal` / `.oryq-shm`, `document-model.md`, `transactions.md`, `indexing.md`, `query-language.md`, `ffi.md`, and `compatibility.md`).

## Goals vs. Non-Goals

* **In-Scope Goals:**
  * Single-file transactional persistence (`.oryq` main database file + `.oryq-wal` write-ahead log + optional `.oryq-shm` multi-process coordination sidecar) portable across Linux, Windows, and macOS on x86-64 and ARM64.
  * `OryqDoc` little-endian binary document format with sorted field-offset directories ($O(\log k)$ zero-copy field extraction) and state-normalized slotted-page delta patches guarded by a 64-bit field-hash bloom bitmask.
  * Logical-page slotted B+ tree storage engine with WAL, lock-free MVCC snapshot reads, zero-delay leader-follower group-commit writer, and bounded snapshot/WAL retention quotas.
  * Primary, nested-field, prefix-compressed compound (with $R=16$ restart points), and multi-key array indexes using canonical memcomparable key encoding.
  * Memory-bounded streaming cursor query engine (`find`, `count`, `explain`, `explain_analyze`) and phased aggregation pipeline (`$match`, `$project`, `$sort`, `$limit`, `$skip`, `$group`, `$unwind`, `$lookup`).
  * Safe Rust API (`oryq-core`), panic-contained C ABI (`oryq-ffi` / `include/oryq.h`) with both JSON and zero-copy `OryqDoc` binary accessors, and diagnostic CLI (`oryq-cli` / `oryq`).
  * WAL-backed `PluggableIndex` trait in `oryq-core` with compile-time feature-gated `oryq-fts` and `oryq-vec` crates in Phase 3.
* **Out-of-Scope Non-Goals:**
  * Network daemon, TCP wire protocol, MongoDB wire-protocol server, distributed consensus (Raft/Paxos), or horizontal sharding.
  * SQL query parsing or relational table schemas.
  * Binary file format compatibility with LiteDB or SQLite database files.
  * Multi-writer concurrent B+ tree page-latch crabbing (all writes serialize through the single-writer / leader-follower group-commit pipeline).
  * Uncoordinated external files for FTS or Vector indexes outside the transactional page manager and `.oryq-wal`.

## Alternatives Weighed

* **Physical Copy-on-Write (CoW) B+ Tree (LMDB / `redb` shadow paging):** Rejected by author: Mutating a single leaf page or appending a sub-document delta requires rewriting every ancestor internal node up to the root ($O(\text{height})$ full-page writes per transaction), which negates the write-amplification savings of slotted-page deltas and causes file bloat when long-lived readers block page reclamation.
* **Log-Structured Merge (LSM) Tree (RocksDB style):** Rejected by author: Multi-file SSTable directory layouts violate the single-file portability requirement (`docs/draft-spec.md` Section 5.2), and background compaction threads cause latency spikes and read amplification on point lookups.
* **Standard BSON On-Disk Representation:** Rejected by author: Standard BSON encodes fields as length-prefixed sequential elements, requiring an $O(k)$ linear scan to locate any field and preventing $O(\log k)$ random field extraction during query filtering and projection.
* **Unbounded Operation-Log Delta Chains in Slotted Pages:** Rejected by author: Chaining raw operation logs (`$inc`, `$push`, `$pull`) forces readers to execute update operators and allocate heap memory on read, destroying zero-copy extraction and coupling `storage/` compaction to `document/` operator semantics. Replaced with state-normalized value patches, a 64-bit slot bloom bitmask, and a hard cap of `MAX_DELTA_CHAIN = 4`.
* **Mandatory Per-Transaction OS File Locks (`fcntl` / `LockFileEx`) in All Modes:** Rejected by author: Invoking kernel file-lock syscalls on every read and write transaction penalizes single-process multi-threaded applications. Replaced with a one-time connection-lifetime OS lock at `Database::open()` in default Single-Process mode and an opt-in `.oryq-shm` mode for multi-process workloads.
* **User-Space Spinlocks or Rust Slice References (`&[u8]`) Over `.oryq-shm` Shared Memory:** Rejected by author: Creating Rust references over cross-process mutable `mmap` memory is Undefined Behavior under the Rust/LLVM memory model, and user-space spinlocks deadlock permanently if a process dies via `SIGKILL`. Replaced with raw-pointer atomic operations (`*const AtomicU64`) paired with 1-byte OS kernel file locks per process slot for automatic crash detection.
* **Baking Full-Text Search and Vector Search Directly into `oryq-core`:** Rejected by author: Including tokenizers, stemmers, inverted posting lists, and HNSW vector graphs unconditionally in the core crate violates minimal binary size and Section 25 of `docs/draft-spec.md`. Replaced with a transactional `PluggableIndex` substrate in `oryq-core` and feature-gated `crates/oryq-fts` and `crates/oryq-vec` crates in Phase 3.
